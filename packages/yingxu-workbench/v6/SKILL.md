# Mellow V6 修订3：仅按广告主体剧情命名

本规则在 V5 基础上删除角色性别字段、合并原文视觉补充，并将职业与身份扩充到20项，作为独立版本使用。读取 [完整分类定义与200个短码](references/rules.txt)；生成及解析以 [机器字典](references/tags.json) 为唯一来源。不得沿用 V3 的字段位置，也不得把旧短码无检查地搬入 V6。

## 固定结构

```text
Mellow_日期_渠道_投放代码_制作代码_语言_形式_一级分类_人物组合_POV_受众配对_关系设定_性格特征_职业身份_物种_情绪关系氛围_主题世界观_艺术形式_渲染风格_人物审美_画面视觉氛围_外观特征_序号_V6
```

共24字段：7个元数据字段＋15个分类字段＋序号＋V6。下划线 `_` 分字段，`+` 分同字段多标签，扩展名不占字段。日期来自原文件，人员代码沿用用户约定，缺少必要元数据时询问，不用当前日期或猜测身份代填。

| 位置 | 分类 | 判定对象 |
|---|---|---|
| 1 | 一级分类 | 唯一核心卖点分类 |
| 2 | 人物组合 | 画面人数与组合 |
| 3 | 用户视角 POV | 文本对用户视角的设定 |
| 4 | 受众与配对 | 文本明确的配对与互动结构 |
| 5 | 关系设定 | 有证据的关系设定 |
| 6 | 性格特征 | 持续行为或明确描述 |
| 7 | 职业与身份 | 20项职业或身份，逐项依字典判定 |
| 8 | 物种 | 设定物种，不是外观或比喻 |
| 9 | 情绪与关系氛围 | 剧情、互动与情绪走向 |
| 10 | 主题与世界观 | 背景、时代、来源、叙事类型 |
| 11 | 艺术形式 | 制作呈现形式 |
| 12 | 渲染风格 | 照片级、写实、半写实、风格化 |
| 13 | 人物审美 | 外形审美，不替代身份 |
| 14 | 画面视觉氛围 | 画面视觉呈现 |
| 15 | 外观特征 | 发色、服饰等，含银白发sh和叙事年龄差x2 |

每个字段必须占位，但不是每类都必然存在真实标签。`unk` 表示尚不确定，只能用于草稿；`na` 表示已经检查、没有任何适用标签，需要逐类写明原因。两者不是200个正式标签。普通人类使用 hu；职业未提供时可用 na 占位并记录“未提供职业，不加职业标签”，不必强制推断职业。

建议数量遵循字典。一级分类、人物组合、POV、艺术形式、渲染风格各一个主要值；其余按证据多选。多角色没有统一POV或统一画风时，不强塞主要值掩盖冲突：在台账记录角色级差异，当前单值字段用合适的通用值或待确认，不擅自扩词。

## 分类证据与边界

- 所有广告素材统一只按主体剧情画面、剧情字幕、开头钩子文案和可核验的语音对白分类。忽略片尾角色简介、角色设定卡、推荐角色卡、标签胶囊、下载落地页、品牌海报与Logo群像；不从这些内容补充或否定主体剧情标签。用户明确解释当前剧情可作为依据。具体检查流程见 [主体剧情证据规则](references/evidence-policy.md)。
- 只用字典内标签，不脑补财富、取向、身份、物种或关系。没有明确依据时宁缺勿错。不能凭真人外貌推断性取向、跨性别身份或非二元身份；仅依据本人明确披露或虚构角色的明确设定。
- 男女同框不是 mxf 的充分依据，男男同框不是 mlm 的充分依据；日漫画风不等于动漫来源，多人画面不等于多角色卡。人物组合、受众配对、一级分类及艺术形式分别判断。
- POV 按参考文档的顺序：明确指定用户性别优先；明确异性关系且AI角色性别已知时取对应用户视角；明确同性关系且角色性别已知时取同一性别视角；已检查主体剧情且没有性别限制时取 any pov。无法核验关键剧情时标 `unk`；不为补齐POV而查片尾设定。
- 一级分类从10项中选一：暗黑恋爱、慢热、纯爱、禁忌之恋、精英世界、幻想世界、LGBT、动漫来源角色、多角色或分支场景、暧昧情欲。以核心卖点为准，不设“只要有某标签就强制归类”的优先级；若多个分类都符合且主卖点不明，标记待确认。剧情、来源或身份的其他信息仍可进入对应的标签字段。
- 敌人变恋人需要真实敌对，不是普通斗嘴；囚禁需要实际限制人身自由；老钱需要代际财富；亿万富翁需要明确极端财富；病娇需要极端行动，不能只因嫉妒贴标签。具体判定要求见字典中英文规则。
- 保留参考文档原有分组：黑帮和反派在性格组，吸血鬼和狼人在主题组；本次不擅自挪动这些词。年龄差 x2 位于外观特征，但必须有叙事证据，不能靠人物外貌判断。
- 银白发只使用外观特征 sh，原 x1 已合并去重；年龄差 x2 也属于外观特征。情绪浪漫与画面浪漫仍分别判断。

## 短码与长度

全部200个正式短码全局唯一，统一2位，第一位为小写字母，第二位为小写字母或数字。字典保留原有两位码，如 `bh`、`sm`；更长编码已经压缩。只能查字典，不能凭英文或数字猜标签。不要求编码连续，也不能按排序重新编号。

固定结构已改变，新协议使用 V6；V5历史名称仍按原字典读取。见 [V5迁移规则](references/v5-to-v6.json)。不能直接删除未知字符串或重新解释退役短码。角色性别只是不再进入名称；判断POV或配对仍可参考明确文本中的角色信息，不凭外貌推断。

15字段各放一个两位标签时，标签段固定44字符（30个标签字符＋14个下划线）；每增加一个同类标签，`+xx`增加3字符。内部建议≤120 ASCII字符，121–180复核，超过180拒绝；不是已核实的Meta上限。

职业与身份保留骑士、老钱、教授、医生、保镖、虚拟主播，新增首席执行官、创业者、律师、警察、侦探、军人、教师、护士、科学家、工程师、演员、歌手、职业运动员、管家，共20项。默认选1–2个有证据的主身份；同一身份的上下位词不机械重复。例如仅有教授身份时不再补教师，仅有CEO身份时不自动补创业者。职业不由衣着推断。旧名中的角色性别码不再进入V6名称。

项目、日期、渠道、人员、语言、VID/IMG保持原约定，不擅自缩写。`unk`仅草稿允许。状态码不是正式标签。人员和元数据中的同字符不参与标签搜索。

## 生成和校验

Python 3标准库即可运行，无网络或数据库依赖。以下路径相对于本Skill目录。

```bash
python3 scripts/naming.py audit
python3 scripts/naming.py generate --input references/example.json
python3 scripts/naming.py validate '完整名称' --reasons reasons.json
```

输入结构见 [示例](references/example.json)：15个中文分类键必须齐全，新短码为数组；`date`为原日期，`serial`为至少三位数字字符串；`na_reasons`逐类记录不适用原因。独立校验时 `--reasons` 指向“大类名→原因”的JSON对象。`--draft`允许 `unk`，正式交付不允许。脚本负责字段、短码、位置、长度和格式，不能代替素材内容判断。

## 旧版迁移和交付

V2/V3/V4/V5历史名称及报表默认保留；只有用户要求迁移时，基于原素材主体剧情重新分类。可直接复用的视觉码也须检查新字段位置。旧“关系与情节”需要拆到关系、性格、职业、主题、情绪等多个新字段；不得仅根据旧码含义机械挪动，判定标准已收紧。V3的 `etl` 不能仅凭旧中文“欢喜冤家”就转成新“敌人变恋人”；旧 `mys` 也不能直接推成叙事悬疑。

只请求建议时输出完整名称和映射表；请求输出素材时默认创建重命名副本，明确要求原地改名时按其范围执行。先验证整批名称及目标重名，禁止覆盖目标或删除源素材。映射表保留原名、新名、原日期、15类中文、证据、待确认项和适用版本。失败项单独报告，不用猜测标签补齐成功数。

解析时去掉扩展名，检查24字段，第8–22字段按 `+` 拆分并验证大类归属。筛选完整短码，不能搜子串或元数据。跨类默认AND、同类默认OR。计数按素材ID去重，各Tag行不可相加。

命名任务不执行角色档案JSON分类流程。用户若另行明确要求角色档案分类，应作为独立任务处理；结果不能反向覆盖本素材主体剧情标签。

## 视频复核补充（规则修订3）

优先结合开头钩子字幕、逐段对白、语音转写和实际互动判断情境；不能仅因亲密动作或暖光归为纯爱。区分看到的字幕与语音转写，识别失败必须说明，不声称已听过。暧昧开房情境可归 sr，但不能把暗示升级为已经发生一夜情。用户明确提供的女性POV、mxf、人类设定属于分类依据；没有这些信息时不凭手部外貌推断。原名TMM是方向拼音缩写，在本项目迁移时删除，不并入制作人员字段。

短码字典和字段结构不变，名称仍以 V6 结尾。本包规则修订号为3；仅识别依据升级，不自动改动既有素材或历史报表。
