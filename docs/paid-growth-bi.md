# 投放数据：同一应用内的 BI 页面

`paid-growth-bi` 的核心报表逻辑迁入决策中心 React / NestJS：入口 `/data`，接口 `/api/growth-decision/bi/*`。不是 iframe，不需要 Next.js、3001 端口、第二个登录或新的密钥。原独立工程没有删除或改动。

## 使用

1. 公司 Mac 运行原更新脚本 `zsh scripts/company-mac/update.sh`，仍使用 8081 服务。
2. 顶部进入“投放数据”，点击“同步有投放的产品”并确认。最近 30 天有实际消耗的产品按 `app_id + media_source` 建档，已有规则、历史、账户配置不覆盖。
   Facebook 系列名称包含 `w2a`（大小写不敏感）时归入 Facebook Web，即使 Doris 的 `media_source` 返回 `facebook`；原本标记为 `facebook_web` 的系列也保留在 Web，其他 Facebook 系列仍归 Facebook。投放数据页的产品、渠道均可选择“全部”；“产品”维度按产品汇总，“渠道”维度跨产品逐渠道汇总。消耗、D0 收入与事件使用同一系列名称口径，不按渠道比例分摊。选择特定渠道时，顶部消耗及每日完整性表只显示该渠道；缺失或过期的投放查询显示缺数，不写成零。
3. 新产品先在指标库配置本产品标准，再在产品页抓取数据。所有产品共用系列决策、分析、实验、观察和规则功能，但不共用达标阈值。
4. 日期默认今天；未指定产品或渠道时默认“全部”，可直接查询。日期在同一个日历里连续点选起止日期（同一天点两次），最多一次查询 31 天。今天、昨天、本周（周一至今天）、上周（周一至周日）快捷按钮仅设置范围。产品、渠道、日期及图中的查看维度可先组合；维度至少选择一个，多选时按所选维度交叉分组。只有点击“查询数据”或“重新拉取”才开始当前报表的 Doris 查询，不自动预取其他维度。首次打开页面的产品选项只读本地产品目录和已有发现缓存；“同步有投放的产品”是单独的显式 Doris 操作。重新拉取绕过缓存。明细显示全部查询结果，不分页；在表格内滚动，表头和首列固定。
5. 从明细“查看决策”跳转产品 / 系列；产品页可返回带产品和渠道筛选的数据页。多个账户匹配时不猜测账户。

## 完整性与指标

- 共用服务端 Doris 只读传输和请求并发限制；浏览器拿不到 MCP 凭据。公司现有 Basic 登录及写请求同源校验适用于新接口。
- 为识别 `w2a`，BI 查询需要返回广告系列 ID / 名称后再汇总，结果仍经完整性校验；缓存保留原始行，展示时派生渠道。产品发现接口无法在无系列名称的汇总中计算 W2A 消耗，因此可提供 Facebook Web 筛选项但不会伪造其 30 天消耗；实际数值以查询日明细为准。
- 每个日期、维度组合、产品、渠道、指标的完整结果独立保存在原 SQLite 的 `growth_bi_cache`，5 分钟有效。一次只查询确认后的组合，不预取其他组合。缓存有效载荷最多 128 MiB、1500 个分片，按更新时间淘汰旧数据（SQLite 文件可能保留可复用空闲页）。失败保留尚未淘汰的旧缓存并标为过期，不覆盖决策快照。长区间首次查询较慢，页面会显示进度。
- 达到 1000 行递归按维度拆分，核对可加总指标；无法拆分或汇总不一致则不发布。每个分片任务最多 300 请求，建议用产品和渠道筛选减少负载。
- CPI 分别展示 Adjust 与媒体口径；买量 CPM 与变现 eCPM 不混用。
- 此页当前 D0 收入 / 全媒体消耗：不筛选 observation_complete，包含尚未完成观察期但已入库的数据。它是查询时的 Doris 数据，不是广告平台实时直连；仍受源头入库延迟影响。决策页的成熟 cohort 判断不变。缺失不当作 0，收入事件数不当作付费人数。
- 从系列跳入决策页按 campaignId 定位，并以蓝色边框和文字标记。单一匹配自动打开详情；跨账户多匹配时不猜测账户。未生成快照时明确提示先抓取，不跳到其他系列。
- 广告组没有 cohort 维度，不分摊系列收入伪造广告组 D0。无归属账户的渠道保持原有安全拦截，不能自动作出账户级操作。
- 原 BI 的独立升级页面及硬编码产品目标未迁入；产品目标使用现有指标库。高级留存/变现分析需要独立数据口径，当前页面不推算缺失指标。

此更新不触发广告投放变更，不删除任何业务历史，不自动覆盖产品规则。

# 广告组事件目标与明细浏览（2026-09-21）

- 事件筛选使用广告组设置：APP_INSTALLS 显示 install，PURCHASE 显示 purchase，自定义事件优先保留 `promoted_object.custom_event_str`，不会把 Arppu_middle 简化成 OTHER，也不从广告名称推断。仅有 custom_conversion_id 时显示 ID，名称仍需源接口返回。
- 一个系列可以包含多种广告组事件；筛选命中整个系列，系列汇总金额不按事件重新分摊。当前 Meta 配置不代表历史某日配置。
- 明细取消 50 条分页，展示全部已查询记录；同一个滚动容器冻结表头、首列。查询范围仍限制 31 天，沿用有上限的服务端缓存，不会为了翻页重复查询 Doris。
- 点击系列名称打开产品/渠道、Facebook Account ID、Campaign ID 与截止查询结束日的近 7 天日级趋势。趋势串行读取并复用缓存，弹窗仅保存选中系列的每日结果，关闭时取消请求。未唯一定位的账户不猜测，缺失日不补成零。
- “进入决策中心”仍按 campaignId 定位，专用于进一步诊断和判断。
- 事件字段依据 Meta 官方 SDK：<https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/adpromotedobject.py>。MCP 若省略自定义子字段，必须报告名称缺口，不能假定所有事件已同步。
