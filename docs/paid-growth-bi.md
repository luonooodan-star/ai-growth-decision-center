# 投放数据：同一应用内的 BI 页面

`paid-growth-bi` 的核心报表逻辑迁入决策中心 React / NestJS：入口 `/data`，接口 `/api/growth-decision/bi/*`。不是 iframe，不需要 Next.js、3001 端口、第二个登录或新的密钥。原独立工程没有删除或改动。

## 使用

1. 公司 Mac 运行原更新脚本 `zsh scripts/company-mac/update.sh`，仍使用 8081 服务。
2. 顶部进入“投放数据”，点击“同步有投放的产品”并确认。最近 30 天有实际消耗的产品按 `app_id + media_source` 建档，已有规则、历史、账户配置不覆盖。
3. 新产品先在指标库配置本产品标准，再在产品页抓取数据。所有产品共用系列决策、分析、实验、观察和规则功能，但不共用达标阈值。
4. 选择产品、渠道、日期和维度，点击查询；重新拉取绕过缓存。最多一次查询 31 天，串行按日显示进度。明细每页 50 条只是显示分页，不是取数上限。
5. 从明细“查看决策”跳转产品 / 系列；产品页可返回带产品和渠道筛选的数据页。多个账户匹配时不猜测账户。

## 完整性与指标

- 共用服务端 Doris 只读传输和请求并发限制；浏览器拿不到 MCP 凭据。公司现有 Basic 登录及写请求同源校验适用于新接口。
- 每个日期、维度、产品、渠道、指标的完整结果独立保存在原 SQLite 的 `growth_bi_cache`，1 小时有效。失败保留旧缓存并标为过期，不覆盖决策快照。
- 达到 1000 行递归按维度拆分，核对可加总指标；无法拆分或汇总不一致则不发布。每个分片任务最多 300 请求，建议用产品和渠道筛选减少负载。
- CPI 分别展示 Adjust 与媒体口径；买量 CPM 与变现 eCPM 不混用。
- 此页成熟 D0 收入 / 全媒体消耗，与决策页匹配 cohort 消耗口径可能不同。缺失不当作 0，收入事件数不当作付费人数。
- 广告组没有 cohort 维度，不分摊系列收入伪造广告组 D0。无归属账户的渠道保持原有安全拦截，不能自动作出账户级操作。
- 原 BI 的独立升级页面及硬编码产品目标未迁入；产品目标使用现有指标库。高级留存/变现分析需要独立数据口径，当前页面不推算缺失指标。

此更新不触发广告投放变更，不删除任何业务历史，不自动覆盖产品规则。
